# Internationalization

The CrystalFramework frontend uses `react-i18next` for internationalization with on-demand dynamic loading of language files. Translation files are located at `web/src/i18n/locales/` and are named using standard language tags (e.g., `en-US.ts`, `zh-CN.ts`).

## Key Structure

All i18n keys are organized under the following top-level namespaces:

| Namespace | Usage | Example |
|-----------|-------|---------|
| `pages` | Page-level text | `pages.userManager.title` |
| `components` | Component-level text | `components.dashboard.myJoinedTenants.title` |
| `entityNames` | Entity names | `entityNames.user` |
| `enums` | Enum value translations | `enums.tenantMemberStatus.4` |
| `menu` | Sidebar menu items | `menu.admin.users` |
| `api` | Common API messages | `api.sessionExpired` |

## Key Naming Conventions

- Always use **camelCase**
- Order from general to specific: `{namespace}.{module}.{section}.{field}`
- **Page-level** keys start with `pages.{pageName}`, suitable for page titles, filter labels, form fields, etc.
- **Component-level** keys start with `components.{componentName}`, suitable for reusable component internal text
- **Column headers** are placed under `components.columns.{entityName}`
- Use **`{{variableName}}`** interpolation instead of string concatenation, e.g., `"Total {{total}} item(s)"`

## How to Add

1. Add translations in `web/src/i18n/locales/{locale}.ts`
2. Use `useTranslation()` in your component to get the `t` function

### Code Example

```tsx
// locales/en-US.ts
pages: {
    myCustomPage: {
        title: 'My Page',
        subtitle: 'This is my custom page',
    },
    myCustomPage: {
        filter: {
            status: 'Status',
            type: 'Type',
        },
    },
},
components: {
    myComponent: {
        placeholder: 'Please enter...',
        confirmText: 'Confirm',
    },
},

// In a page component
import { useTranslation } from 'react-i18next';
import { ActionBarComponent } from '@/components/ActionBarComponent.tsx';

function MyPage() {
    const { t } = useTranslation();

    return (
        <ActionBarComponent
            title={t('pages.myCustomPage.title')}
            subtitle={t('pages.myCustomPage.subtitle')}
        />
    );
}
```

## Interpolation Syntax

Use `{{variableName}}` as placeholders in language files, and pass actual values as the second argument to `t()`:

```typescript
// Language file
{ "greeting": "Hello, {{name}}!" }

// In component
t('greeting', { name: 'Alice' })
// Output: Hello, Alice!
```

## Enum Translations

Enum values are managed under the `enums` namespace and registered in `enum-helpers.ts` with accessor functions:

```typescript
// In i18n-rules.ts type definition
enums: {
    tenantMemberStatus: { 0: string; 1: string; 2: string; 3: string; 4: string };
}

// In enum-helpers.ts registration
export const getTenantMemberStatus = (status: number): string =>
    i18n.t(`enums.tenantMemberStatus.${status}`);
```

## Settings SDK: Adding i18n for Custom Declarations

The System Settings / Tenant Settings management pages are fully data-driven: the backend declares settings items dynamically via `SystemSettingsRegistry` / `TenantSettingsRegistry`, and the frontend `SystemSettingsManagerPage` renders controls automatically based on those declarations. When an external module declares a new settings item through the SDK (e.g. registering visibility for a custom `ResourceFileType`), you only need to add i18n entries as shown below — no page/component code changes required.

### Prerequisite: SDK Registration Entry Point

Frontend plugins declare their keys / groups / tabs through `pluginRegistry` in `@/plugin/registry.ts`. Once registered, the three Maps in `web/src/i18n/system-settings.tsx` will automatically resolve translations via a fallback path.

```typescript
import { pluginRegistry } from '@/plugin/registry';

// Call once from the plugin's bootstrap entry
pluginRegistry.addSettingsKey('system', 'resource.visibility.myFileType');
pluginRegistry.addSettingsGroup('system', 'resource.visibility'); // skip if group already exists
pluginRegistry.addSettingsTab('system', 'resource');              // skip if tab already exists
```

### Step 1: Add the Key Translation

`pages.systemSettingsManager.keys.<key>` is used as the settings item label. The key is a dot-separated path that must match the backend `SettingsItemDeclaration.key` exactly.

```typescript
// locales/en-US.ts
pages: {
    systemSettingsManager: {
        keys: {
            'resource.visibility.myFileType': 'My File Type Visibility',
        },
    },
},
```

### Step 2: If Introducing a New Group / Tab, Add Its Translation

`pages.systemSettingsManager.groups.<group>` and `pages.systemSettingsManager.tabs.<tab>` are used for group / tab labels. Skip this step if you're reusing an existing group (e.g. `resource.visibility`) and tab (e.g. `resource`).

```typescript
// locales/en-US.ts
pages: {
    systemSettingsManager: {
        groups: {
            'myModule.mySection': 'My Group',
        },
        tabs: {
            'myModule': 'My Tab',
        },
    },
},
```

### Step 3: For Enum-Typed Declarations (`ENUM_SINGLE` / `ENUM_MULTIPLE`), Translate Each Enum Value

The management page resolves each dropdown option through `pages.systemSettingsManager.enums.<settingsKey>.<enumValue>`. **Note that `settingsKey` here is the full settings key, not the enum type name** — even when multiple settings share the same backend enum, you must write a dedicated enum translation block per key (matching how the built-in declarations do it, see `resource.visibility.userAvatar` / `resource.visibility.tenantIcon` etc.).

```typescript
// locales/en-US.ts
pages: {
    systemSettingsManager: {
        enums: {
            'resource.visibility.myFileType': {
                'PUBLIC': 'Public (anyone)',
                'AUTHENTICATED': 'Authenticated users',
                'SCOPE_MEMBER': 'Same-tenant members',
                'OWNER_ONLY': 'Uploader only',
                'SYSTEM_ADMIN': 'System admin only',
            },
        },
    },
},
```

### Cheat Sheet

| Step | File | Content |
|------|------|---------|
| 0 | Plugin bootstrap entry | `pluginRegistry.addSettingsKey('system', '<key>')` |
| 1 | `src/i18n/locales/{locale}.ts` | `pages.systemSettingsManager.keys.<key>: '...'` |
| 2 (optional) | `src/i18n/locales/{locale}.ts` | `pages.systemSettingsManager.groups.<group>: '...'` / `tabs.<tab>: '...'` |
| 3 (enum type) | `src/i18n/locales/{locale}.ts` | `pages.systemSettingsManager.enums.<key>: { <enumValue>: '...' }` |

::: tip No Page Changes Required
Once the above is in place, `SystemSettingsManagerPage` will automatically render the new item under the `resource` tab / `resource.visibility` group — no tsx page/component changes needed.
:::

::: warning Cross-Language Sync
`docs/develop/frontend/i18n.md` and `docs/en/develop/frontend/i18n.md` must be kept in sync; `web/src/i18n/locales/zh-CN.ts` and `en-US.ts` must have a one-to-one entry correspondence.
:::
